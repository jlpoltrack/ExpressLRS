# DroneCAN

## MAVLink DroneCAN setup

ESP32 and RP2350 receivers. Connect a CAN transceiver to the `can_rx`/`can_tx` pins of the hardware layout, or to the receiver's serial RX and TX pins if the layout has none, set the receiver's serial protocol to `MAVLink DroneCAN`, and use the MAVLink link mode on the TX module. The receiver is fixed at node ID 68 and 1Mbit/s.

On ESP32 the TWAI controller is used (`TWAIDriver`) and the node runs in the main loop. On RP2350 CAN is done in software on PIO2 by [can2040](https://github.com/KevinOConnor/can2040) (`CAN2040Driver`). The whole node runs on core 1: the PIO IRQ, libcanard and every DroneCAN message (`DroneCANNode`), so the radio code on core 0 cannot delay it. Only `SerialDroneCAN`, the MAVLink side, runs on core 0, and it exchanges RC and tunnel bytes with core 1 through lock-free rings. Core 1 is halted while the config is written to flash, so CAN frames go unacknowledged for that time and the FC resends them.

ArduPilot parameters, shown for the first CAN port and driver:

| Parameter | Value | Notes |
|---|---|---|
| `CAN_P1_DRIVER` | 1 | |
| `CAN_P1_BITRATE` | 1000000 | Default |
| `CAN_D1_PROTOCOL` | 1 | DroneCAN |
| `CAN_D1_UC_SER_EN` | 1 | Reboot to show the `S1` parameters |
| `CAN_D1_UC_S1_NOD` | 68 | Receiver node ID |
| `CAN_D1_UC_S1_IDX` | 0 | |
| `CAN_D1_UC_S1_PRO` | 2 | MAVLink2 |
| `RC_PROTOCOLS` | 1 (All), or include bit 14 | DroneCAN RC input |
| `RSSI_TYPE` | 3 | Optional, link stats from the receiver |

RC is sent as `dronecan.sensors.rc.RCInput`, so `RC_CHANNELS_OVERRIDE` is not used. RC and MAVLink work on ArduPilot 4.6; the link stats (RSSI dBm, LQ, SNR, TX power) need 4.7, and older versions show them as a meaningless RSSI.

Only one receiver per vehicle is supported, as ArduPilot does not arbitrate between DroneCAN RC sources.

## Firmware update (RP2350)

The receiver accepts `uavcan.protocol.file.BeginFirmwareUpdate` and fetches the image with `uavcan.protocol.file.Read` from the file server, e.g. the DroneCAN GUI Tool or Mission Planner connected to the FC (SLCAN or MAVLink CAN forwarding). Serve the configured `firmware.bin` from the build folder, which has the options and hardware layout appended, never the `.elf`, which has neither. `tools/dronecan_fw_update.py` does the update through the FC's MAVLink CAN forwarding, also takes the `firmware.uf2` built alongside, and can verify the flash afterwards over USB.

The app runs from RAM, so the image is written straight over the old one in flash while the receiver keeps running (`DroneCANFwUpdate`). Updates are refused while connected to a TX: a TX can commit config to flash (Lua, binding), and the connection is also what arming needs. Sectors 0-3 are buffered and checked before flash is touched; sector 0, which holds the boot block, is then erased first and written last, so an interrupted update leaves no bootable image and the next power cycle lands in BOOTSEL for a USB reflash. Until then NodeStatus reports health CRITICAL, and a new update can be started. During an update NodeStatus mode is SOFTWARE_UPDATE with the KB received as the vendor status code; the receiver reboots as soon as the image is complete and verified.

Flash is written from core 1 with its interrupts off, which is what keeps core 0's own flash writes (config, LittleFS) from interleaving: they idle core 1 by doorbell and wait for it to answer. Two costs follow. Each 4 KB sector erase (typically 45 ms, up to 400 ms on common W25Q parts) is also a CAN receive blackout, as can2040's IRQ runs on core 1, and frames from the FC in that window are lost; the transfer itself is unaffected, as the next read is only requested once the write is done. And a core 0 config commit that lands in such an erase spins with core 0's interrupts off for the same time, which would glitch the RF link once; refusing updates while connected leaves only the power-on counter commits in the first seconds after boot.

Through ArduPilot's MAVLink CAN forwarding an update runs at about 4 KB/s, under a minute for a 200 KB image.

## DSDL

`dsdl/` holds C serialisers generated by [dronecan_dsdlc](https://github.com/dronecan/dronecan_dsdlc) for the messages used by MAVLink over DroneCAN (`SerialDroneCAN`). They are used with [libcanard](https://github.com/dronecan/libcanard), which is fetched through `dronecan_lib_dep` in `targets/common.ini`.

Generated from:

- DSDL `b4653c7abc3c47cb31b16efa24ea755232774756`, which is newer than ArduPilot's submodule and adds the RCInput `QUALITY_TYPE` constants
- dronecan_dsdlc `de47a8972b7d8c59e50c3acfab5754db29798caa`

## Regenerating

Run this from a scratch directory, with `ELRS` pointing at this repository:

```sh
git clone https://github.com/dronecan/DSDL && git -C DSDL checkout b4653c7
git clone https://github.com/dronecan/dronecan_dsdlc && git -C dronecan_dsdlc checkout de47a89
pip install -r dronecan_dsdlc/requirements.txt
python3 dronecan_dsdlc/dronecan_dsdlc.py -O out DSDL/uavcan DSDL/dronecan

for f in "$ELRS"/src/lib/DroneCAN/dsdl/*; do
    # Local headers use quoted includes so they resolve from this library's folder
    sed -E 's/#include <((canard\.h|uavcan\.|dronecan\.)[^>]*)>/#include "\1"/' \
        "$(find out -name "$(basename "$f")")" > "$f"
done
```

Only the files already in `dsdl/` are kept. To use a new message, copy its `.c`/`.h` and those of any types it depends on.
